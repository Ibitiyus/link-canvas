# ZIN: готовность к публичному запуску

Аудит этапа 8 охватывает код репозитория, все SQL-миграции, Edge Function, сохранение, Auth и браузерные взаимодействия. Это не проверка настроек удалённого Supabase/Vercel: доступ к production не использовался. Ни обязательное подтверждение email, ни регистрация, ни секреты рабочего сервиса не изменялись.

## Риски и приоритеты

|---|---|---|---|
| R1 | High | Автосохранение и cleanup эффекта могли записать старую версию поверх другой вкладки | Исправлено: проверка исходной версии, отдельный журнал вкладки до записи, остановка перезаписи, выбор версии и восстановление |

| R16 | Medium | SMTP, подтверждение email, CAPTCHA, глобальные тарифные квоты и perimeter rate limits нельзя проверить по исходникам | Перед публичным запуском владелец проверяет настройки, перечисленные ниже |
| R17 | Low | Сторонние HTTP(S) изображения, SVG в img, шрифты и плееры могут исчезнуть или отслеживать посетителя | HTML/JS не вставляются; SVG-файлы/data SVG запрещены, удалённый SVG только как img; внешние URL остаются сознательной возможностью автора |
| R18 | Low | Общий CSP/headers не были заданы в конфигурации хостинга репозитория | Подготовлен неактивный пример headers; включение и проверка остаются у владельца |

Подтверждённых Critical уязвимостей в проверенном коде не обнаружено. Это не гарантия отсутствия неизвестных уязвимостей и не аттестация production. Исправлены найденные High риски в пределах репозитория; применение серверных исправлений к рабочему проекту требует действий владельца.

## Что изменено в репозитории

- Проекты сохраняют прежнюю модель v1. Новых обязательных полей проекта нет. Старые страницы, группы, эффекты, прозрачность, шрифты и JSON поддерживаются.
- `LocalPersistence` сравнивает текущие данные хранилища с исходной версией. До замены создаётся отдельный журнал экземпляра редактора. При одновременной гонке разных процессов оба журнала сохраняют свои версии; пользователь выбирает нужную в восстановлении. Это не распределённая транзакция localStorage.
- Кнопка «Восстановление проекта»: открытие копии, скачивание исходного JSON, явное удаление выбранной резервной копии с подтверждением. Повреждённый исходный JSON тоже доступен для скачивания. Не удаляется автоматически ни исходный проект, ни уникальные recovery-копии.
- Копии восстановления содержат ссылки на IndexedDB/облако, а не переносимые файлы. Для полноценного бэкапа нужен «Экспорт JSON». Если файл недоступен, полный экспорт сообщает ошибку; исходный JSON можно скачать отдельно.
- Мгновенное закрытие процесса/сбой питания нельзя гарантированно обработать. Страница использует отложенное сохранение 350 мс, а уход/скрытие вкладки пытается синхронно сохранить последнюю версию. Сеть не считается надёжным механизмом сохранения при закрытии.
- Облачное сохранение сохраняет CAS по revision, очередь загрузок, привязку запросов к инициировавшему аккаунту. Статусы различают отсутствие сети, ошибку и конфликт. Новые локальные конфликты блокируют автоматическую отправку до выбора версии.
- Edge не принимает произвольные адреса для серверного fetch: копирует только проверенные `cloud:` пути владельца. Сторонние медиа загружаются браузером, а не серверным прокси.
- JS/HTML из пользовательского текста не исполняются. Ссылки разрешают только HTTP(S), без встроенных username/password. Blob URL создаются приложением временно из проверенных локальных файлов, отзываются при размонтировании и не сохраняются как URL проекта.

## Серверные изменения: только новые миграции

Существующие миграции не изменены. Добавлены, в указанном порядке:

1. `202610220001_production_safety.sql`: согласование MIME/расширения, общий бюджет приватных резервирований, бюджет публичных копий, закрытие прямого доступа к внутренним версиям RPC.
2. `202610220002_storage_commit_guard.sql`: совместимость с предварительной проверкой Storage без metadata, финальный триггер размера/MIME для обычных и TUS-загрузок.
3. `202610220003_edge_request_budget.sql`: отдельный бюджет Edge-команд, который фиксируется до основной операции и учитывает её ошибки.
4. `202610220004_reuse_immutable_public_assets.sql`: повторное использование проверенных неизменяемых медиа между ревизиями, включая копии в старых папках; квота считает только предстоящие новые копии.

Применяйте **все четыре**, затем обновляйте Edge Function. Не выкатывайте промежуточное состояние после первой миграции: её строгая предварительная политика заменяется совместимой проверкой во второй. Миграции не удаляют строки и не меняют бакеты/Auth. Пока они не применены к production, серверные риски старой версии там остаются.

Текущие пределы сервера:

| Ресурс | Предел |
|---|---|
| Файл в облаке | Существующий лимит бакетов, по умолчанию 50 МиБ |
| Приватные резервирования аккаунта | 512 МиБ суммарно, до 1000 записей, включая незавершённые |
| Публичные копии аккаунта | 512 МиБ с учётом предстоящего копирования |
| Загрузка / Edge complete-upload | 600/час на аккаунт |
| Публикация | 10/мин на аккаунт, отдельный Edge-бюджет |
| Очистка | 3/час на аккаунт |
| Сохранение | 180/мин на аккаунт, CAS revision |
| Проект в БД | До 200 блоков, 100 групп, 8 шрифтов, существующий предел JSON 4 млн символов |
| Edge-команда | До 16 КиБ |

Это лимиты приложения, **не обещание вместимости бесплатного тарифа**. Множество аккаунтов может исчерпать общую квоту проекта раньше. Незавершённые резервирования учитываются, чтобы ими нельзя было обойти лимит. Существующие данные сверх новой квоты не удаляются: новые резервирования/копирования будут отклонены. Изменять пределы следует отдельной будущей миграцией после оценки тарифа, не редактируя уже применённые файлы.

Публичная очистка намеренно отключена, пока нет атомарного реестра ссылок на публичные файлы. Владелец может провести отдельную ручную ревизию после резервного копирования; удалять «старые папки» только по возрасту нельзя. Старые публичные копии занимают место и могут потребовать повышения квоты.

## Развёртывание: действия владельца

1. Сохраните текущий deploy/commit и резервную копию БД **и Storage**. Проверьте восстановление на отдельном тестовом проекте. Не запускайте `cloud:reset`, `db reset`, `db push` без проверки выбранного проекта и плана изменений.
2. Подготовьте staging Supabase. Проверьте список применённых миграций, выполните новые миграции последовательно, без изменения старых файлов. Для локальной базы команда — `node scripts/supabase.mjs migration up --local`; она не сбрасывает БД.
3. Разверните `supabase/functions/page-actions` после миграций. Убедитесь, что серверные переменные Supabase доступны только Edge, а `ZIN_PUBLIC_SUPABASE_URL`, если задан, содержит внешний HTTPS-адрес вашего Storage.
4. В Vercel проверьте существующие `VITE_SUPABASE_URL`, **публичный** `VITE_SUPABASE_ANON_KEY`/publishable key и `VITE_CLOUD_MAX_FILE_MB`. Не помещайте service_role, `sb_secret_…`, SMTP-пароли в `VITE_*`. Уточните, поддерживает ли выбранная версия CLI/проект используемый тип ключа.
5. Сборка: Node.js 24 LTS (минимум по package.json — 22.12), `npm ci`, `npm run typecheck`, `npm test`, `npm run build`. Настройки framework остаются Vite, output — `dist`, SPA rewrite уже существует.
6. Сначала проверьте preview deploy на тестовом Supabase. Затем объедините PR и выполните обычный deploy production. Не направляйте экспериментальные тесты на рабочую БД.
7. Проверьте `/`, `/editor`, `/templates`, `/preview`, `/u/:username` прямым открытием, регистрацией двух пользователей и анонимным браузером. Выполните checklist ниже.

### RLS и Storage: ручная проверка Supabase

- RLS включён для profiles, drafts, assets, published_pages, publication_jobs, operation_limits. API-роли не должны иметь прямую запись в эти таблицы; владелец читает только свои приватные строки. Анонимно читаются только published_pages.
- У anon/authenticated нет EXECUTE для внутренних `take_operation`, `validate_project`, `validate_effects`, `finish_publication`, `claim_unused_assets`, `reserve_asset_v1`, `begin_publication_v1`, `guard_asset_metadata`, `public_asset_copies`. Authenticated разрешены только необходимые пользовательские RPC, включая `authorize_edge_action`, который работает исключительно с auth.uid().
- `zin-drafts` остаётся приватным; `zin-public` содержит только явно опубликованные копии. Нет клиентской политики записи/удаления публичных объектов. Не добавляйте широкую политику `using(true)` для приватного бакета.
- Bucket MIME allowlist не включает HTML/SVG. Лимиты обоих бакетов и клиентский предел файла должны соответствовать тарифу. Триггер `zin_asset_metadata` проверяет финальные метаданные, а Edge — размер и сигнатуру содержимого.
- Username изменяется через RPC и каскадно обновляет адрес страницы; владелец файлов определяется UUID, не username. Старый адрес перестаёт отдавать страницу.

## Email, подтверждение и восстановление: только владелец

Регистрация не отключалась. Обязательное подтверждение email в production не включалось. Локальные тесты работают с локальным Auth/Mailpit; они **не подтверждают доставку внешней почты**.

1. В Supabase настройте собственного SMTP-провайдера: проверенный отправитель/домен, SPF, DKIM, DMARC, TLS и лимиты отправки. Секреты храните только в настройках провайдера/Supabase.
2. Укажите точный Site URL `https://link-canvas-swart.vercel.app` (или финальный домен). В Redirect URLs разрешите нужные `/login` и `/reset-password`; проверьте использование query next для входа. Не разрешайте произвольные домены/wildcard для production. Для preview используйте отдельный Supabase или конкретные доверенные адреса.
3. Проверьте шаблоны подтверждения и восстановления, PKCE-редиректы и срок действия ссылок. Проверьте реальное письмо в обычный почтовый ящик и спам; откройте ссылку и смените пароль.
4. Только после успешных писем и с вашим отдельным решением включите Confirm email. Проверьте незавершённую регистрацию, повторный вход, уже подтверждённого пользователя и ошибку просроченной ссылки. Не считайте ответ API доказательством фактической доставки.
5. Настройте Auth rate limits по email/IP, защиту от брутфорса и допустимую сложность пароля. Проверьте ограничения тарифа и доступные настройки утечек паролей.
6. CAPTCHA (Turnstile/hCaptcha) рекомендуется перед массовым запуском. **Не включайте серверную CAPTCHA без доработки клиента**, который получает и передаёт captchaToken в signUp/signIn/resetPasswordForEmail. Сейчас виджет/токен не реализованы; иначе вы заблокируете реальные регистрации. Обсудите и выполните это как отдельное небольшое изменение после выбора провайдера.

## Заголовки безопасности

Файл `docs/vercel-security-headers.json` — **неактивный** пример для ручного рассмотрения; `vercel.json` и рабочие настройки не изменены. Объедините headers с существующими rewrites в staging. CSP сначала Report-Only: проверяйте только в Console/Network или настройте отдельный privacy-safe report endpoint. Он не блокирует нарушения, пока вы явно не замените заголовок на `Content-Security-Policy`.

Проверьте Supabase HTTP/WebSocket, TUS, blob/data шрифты, локальные файлы, YouTube, сторонние изображения и GIF. Затем включайте enforcement. При добавлении CAPTCHA потребуется разрешить точные домены провайдера script/frame/connect. Нельзя добавлять unsafe-eval или разрешать любой iframe только ради устранения ошибок. Headers не заменяют RLS и проверку типов файлов.

## Резервное копирование и восстановление

- Автор: регулярно «Экспорт JSON» **с файлами**, особенно перед импортом, заменой версии и очисткой. Проверить импорт копии в отдельном профиле браузера, не поверх единственного рабочего проекта.
- При конфликте вкладок: сначала экспорт обеих версий, затем «Открыть сохранённую» или «Оставить текущую». Recovery-копии остаются доступны. Перед заменой текущего canonical сохраняется его исходная строка.
- При квоте: не закрывать вкладку до выгрузки JSON. «Восстановление» позволяет скачивать/удалять выбранные старые recovery-копии с подтверждением; текущий проект/IndexedDB-файлы этой кнопкой не удаляются. Копии разных запусков могут занимать дополнительное место; автоматической ротации уникальных копий нет.
- При повреждённом JSON: скачать исходные данные через восстановление. Не очищать localStorage в DevTools до копирования. Исходный файл можно анализировать отдельно; редактор не перезаписывает его автоматически первым изменением.
- Владелец: резервировать БД и объекты Storage отдельно; наличие SQL-бэкапа не гарантирует бэкап файлов. Проверить расписание, хранение вне проекта, шифрование, срок хранения и процедуру восстановления. Возможности PITR/автоматических бэкапов зависят от актуального тарифа.
- Общий компьютер: после выхода локальный кеш аккаунта намеренно остаётся для восстановления. Не используйте общий браузерный профиль для секретных проектов; удалять локальные данные следует только после проверенного экспорта. Облачные файлы повторно требуют правильную сессию.

## Мониторинг и бесплатные тарифы

- Наблюдайте Auth/Edge/Storage/DB ошибки, 401/403, частоту конфликтов, 429, 5xx, длительность публикации/загрузки, размеры бакетов, egress и активные соединения. Настройте уведомления по порогам **общего** проекта, а не только аккаунта.
- Не отправляйте в логи project JSON, тексты пользователей, signed URL, email, Authorization, refresh/access tokens или ключи. Внешний error tracker здесь не включён; перед интеграцией настройте scrub полей и согласуйте политику данных. Отдельно контролируйте доступ к dashboard/logs.
- SQL-бюджет успешных RPC не защищает от всех невалидных запросов: rollback отменяет счётчики внутри неуспешной транзакции. Для Edge добавлен отдельный бюджет; для Auth/Data API нужны rate limits шлюза/WAF и защита от автоматических аккаунтов.
- Перед запуском проверьте в кабинетах Supabase/Vercel актуальные общие Storage/egress/DB/Auth/Edge/bandwidth/execution лимиты, стоимость превышения, возможную приостановку проекта и бюджеты оповещений. Числа тарифов не зафиксированы в коде, поскольку они меняются.

## Проверки и границы результатов

Команды: `npm run typecheck`, `npm test`, `npm run build`, `npm run test:e2e`, `npm run test:cloud`, `npm run test:e2e:cloud`. Для публичных renderer-моков используется `ZIN_CANVAS_E2E=1` и production build с фиктивными loopback-переменными; `test:canvas` готовит их автоматически. Локальные cloud-скрипты явно запрещают удалённый адрес и удаляют в cleanup только созданные ими тестовые аккаунты/объекты.

Новые проверки: журналы/конфликты/квота, защита повреждённого JSON, исходные резервные копии, offline flush, инертный пользовательский текст/опасные URL, секреты в ошибках, потоковые границы Edge, recovery при обновлении токена, мобильный Escape/фокус 320/390/768, композиции 100/200 блоков, реальные серверные ошибки и гонка облачной загрузки. Браузерные performance-артефакты содержат loadAndEditMs/domNodes с замедлением CPU ×4; повторное открытие предпросмотра проверяет освобождение IntersectionObserver; это лабораторные измерения Chromium, не p95 реальных устройств и не нагрузочный тест сервиса. WebKit/iOS/Safari и Android на физическом слабом устройстве нужно проверить вручную.

Фактические результаты текущего запуска дополняются в отчёте PR. Нельзя считать тесты удалённого production или доставку SMTP выполненными по результатам локального Docker.
