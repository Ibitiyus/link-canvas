# ZIN: аккаунты, облако и публикация

Актуальный аудит, новые квоты и обязательные ручные шаги перед запуском: [PRODUCTION_READINESS.md](PRODUCTION_READINESS.md).

Реализована одна страница на аккаунт: приватный черновик и отдельная опубликованная версия. Редактор без аккаунта продолжает работать локально. Настоящая доступность из интернета требует развёрнутого Supabase и HTTPS-хостинга приложения; локальный Docker сам по себе этого не обеспечивает.

## Локальная проверка с настоящим сервером

Нужны Node.js 24 LTS и Docker с запущенным daemon / Docker Desktop. Команды выполняются в существующей папке репозитория:

```sh
npm ci
npm run cloud:start
npm run cloud:env
```

Первый запуск скачивает Docker-образы. Миграции применяются при создании локальной базы. `cloud:env` создаёт игнорируемые `.env.local` (адрес и публичный anon key) и `supabase/functions/.env` (публичный адрес для опубликованных файлов). Скрипт разрешает только localhost и не записывает серверный ключ в браузерную конфигурацию. Он заменяет эти два локальных файла; не запускайте его поверх конфигурации удалённого проекта.

В отдельном терминале:

```sh
npm run cloud:functions
```

В основном терминале:

```sh
npm run dev
```

Откройте `http://localhost:5173`. Зарегистрируйтесь через `/register`, откройте `/dashboard`. В локальном тестовом Auth подтверждение email выключено; письма восстановления поступают в Mailpit на `http://127.0.0.1:54324`. В рабочем проекте подтвердите email и настройте отправку писем.

`npm run cloud:stop` останавливает локальные сервисы с сохранением данных. **`npm run cloud:reset` удаляет данные локальной базы** и заново применяет миграции; это команда только для сброса тестовой среды.

Для запуска без облака оставьте переменные из `.env.example` пустыми и перезапустите Vite. Регистрация будет недоступна, но локальный редактор, файлы и JSON продолжат работать.

### Особенность текущей облачной среды

Обёртка `scripts/supabase.mjs` использует документированный `SUPABASE_HOME` внутри игнорируемого `node_modules/.cache` и облегчённые образы (`SUPABASE_USE_SLIM_IMAGES=true`). Домашний каталог менять не требуется. Для обычных образов можно явно задать `SUPABASE_USE_SLIM_IMAGES=false`.

В этой среде Docker получает HTTP-прокси, мешающий внутренним обращениям к Auth/Storage. Если `cloud:start` сообщает только об этих проверках здоровья, выполните `npm run cloud:start -- --ignore-health-check`, затем `cloud:env` и `cloud:functions`. После запуска функции выполните в другом терминале `npm run cloud:direct`: он пересоздаст **только** контейнер `supabase_edge_runtime_zin`, сохранив настройки, монтирования и bootstrap, остановит принадлежащий этому checkout watcher функции и исключит прокси из её внутреннего HTTP-трафика. База и файлы не сбрасываются, TLS-проверки не отключаются. На обычном компьютере этот обход не нужен. После `cloud:direct` локальная функция работает без отдельного watcher; после полного перезапуска Supabase повторите последовательность.

Проверять готовность следует запросами к `/auth/v1/health`, `/storage/v1/status` на порту 54321 и `npm run test:cloud`, а не одним флагом игнорирования healthcheck. Для TUS на localhost клиент исправляет ошибочный HTTPS-адрес продолжения загрузки; адрес рабочего Supabase остаётся HTTPS.

## Подключение рабочего Supabase

1. Создайте отдельный проект Supabase. В SQL Editor выполните целиком `supabase/migrations/202610200001_zin_platform.sql` **один раз в новой базе ZIN**, либо примените миграции через CLI:

   ```sh
   npx supabase login
   npx supabase link --project-ref YOUR_PROJECT_REF
   npx supabase db push
   npx supabase functions deploy page-actions
   ```

2. В Auth включите Email/Password и подтверждение email, настройте собственный SMTP. Укажите Site URL вашего приложения и разрешённые Redirect URLs: `https://YOUR_DOMAIN/login` и `https://YOUR_DOMAIN/reset-password`; для разработки добавьте localhost. Письма используют PKCE: ссылку следует открывать в том же браузере, где запрашивали письмо. Не разрешайте произвольные домены в redirect allowlist. Настройте лимиты Auth и при необходимости CAPTCHA.
3. Миграция создаёт приватный bucket `zin-drafts` и публичный `zin-public`, MIME allowlist и Storage policies. Не делайте `zin-drafts` публичным и не добавляйте клиентские политики записи в `zin-public`. Серверная функция использует встроенные Supabase secrets `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`; их не нужно помещать во фронтенд. `verify_jwt=false` в конфигурации отключает устаревшую проверку шлюза, но **каждый запрос проверяется самой функцией через Auth getUser**, включая новые ключи/JWT.
4. Создайте `.env.local` по `.env.example`:

   ```dotenv
   VITE_SUPABASE_URL=https://YOUR_PROJECT_REF.supabase.co
   VITE_SUPABASE_ANON_KEY=YOUR_PUBLISHABLE_OR_ANON_KEY
   VITE_CLOUD_MAX_FILE_MB=50
   ```

   Используйте публичный publishable / anon key. `service_role` и `sb_secret_` запрещены в `VITE_*`, исходниках и Git. Приложение дополнительно отказывается создавать клиент с распознанным серверным ключом, но ошибочно включённый в сборку секрет всё равно нужно немедленно отозвать.
5. При собственном API gateway укажите серверный secret `ZIN_PUBLIC_SUPABASE_URL` с публичным HTTPS-адресом Storage API. В обычном Supabase используется его встроенный публичный адрес.
6. Выполните `npm run build`, разместите `dist/` на HTTPS-хостинге. Настройте SPA fallback на `index.html` для `/editor`, `/dashboard`, auth-маршрутов и `/u/*`. Переменные `VITE_*` нужны **во время сборки**; после их изменения пересоберите приложение. Адреса `192.168.*`, localhost и порт 5173 не являются публикацией в интернете.

Рабочий Supabase, домен, SMTP и размещение `dist/` не создаются этими исходниками автоматически. Для них нужны проект и настройки владельца. Локальные интеграционные тесты не обращаются к рабочей базе.

## Как устроено хранение

Сохранён формат проекта `version: 1`. Геометрия, слои, фон, стили, восемь типов блоков и шрифты хранятся в JSONB. Бинарные данные находятся только в Storage. Поля источников получают стабильные ссылки `cloud:<owner UUID>/<file UUID>.<ext>`; временные signed URLs не записываются в проект.

| Таблица | Назначение и доступ |
| --- | --- |
| `profiles` | Username и владелец. Только свой профиль; занятость имени — через ограниченный RPC. |
| `drafts` | Один приватный JSONB-черновик и номер ревизии на аккаунт. |
| `published_pages` | Намеренно опубликованный снимок. Разрешено анонимное чтение. |
| `assets` | Владелец, размер, MIME и состояние файла. Только свои записи. |
| `publication_jobs` | Серверный снимок и lease для атомарной публикации. |
| `operation_limits` | Серверные счётчики чувствительных операций. |

У всех таблиц включён RLS. Клиент не пишет напрямую в таблицы: RPC определяют владельца через `auth.uid()`. Серверные помощники недоступны API-ролям пользователя. Username уникален в PostgreSQL, 3–30 символов, начинается с латинской буквы; далее строчные буквы, цифры и `_`. Служебные имена зарезервированы. Изменение username атомарно меняет публичный адрес; старый перестаёт открываться. Возврат старого адреса другому владельцу в будущем не блокируется.

Облачное автосохранение запускается через 1 секунду после изменения. В каждой вкладке один последовательный writer; если во время загрузки появились новые изменения, он сохраняет и их. Сервер сравнивает ожидаемую ревизию с текущей (CAS). При конфликте ничего не перезаписывается: в кабинете можно экспортировать текущую копию, открыть облачную либо явно заменить её. Статус «Облако: сохранено» появляется только после подтверждения сервера. При ошибке сети остаётся локальная копия; событие восстановления соединения повторяет сохранение.

Локальная копия аккаунта хранится отдельно в `zin.account-project.<UUID>`, метаданные синхронизации — в `zin.cloud-sync.<UUID>`. У каждого аккаунта своё пространство; новый аккаунт не получает проект предыдущего. После открытия облачной версии вместо конфликтной локальной сохраняется дополнительная копия `zin.recovery.<UUID>`. На общем компьютере локальные копии и токены остаются данными браузера: после выхода используйте отдельные профили браузера или удаляйте данные сайта только после резервного копирования.

## Файлы и ограничения

Загрузка — TUS с чанками по 6 МиБ, повтором запросов и процентом в индикаторе облака. Поддерживаются PNG/JPEG/WebP/GIF, MP4/MOV/WebM/OGG, MP3/WAV/OGG/M4A/AAC/FLAC/WebM, WOFF/WOFF2/TTF/OTF. Сервер проверяет размер и сигнатуру байтов, не только заявленный MIME. Готовые файлы неизменяемы: замена создаёт новый UUID. HTML/SVG и исполняемые форматы не разрешены. Изображения и GIF не уменьшаются и не перекодируются.

По умолчанию **облачный** лимит — 50 МиБ на файл. Настройте одновременно `VITE_CLOUD_MAX_FILE_MB`, `file_size_limit` обоих buckets, глобальный Storage limit и ограничения тарифа. Изменять bucket limits следует отдельной миграцией, например:

```sql
update storage.buckets set file_size_limit = 104857600
where id in ('zin-drafts', 'zin-public');
```

Это не возвращает ограничение 10 МБ в локальный редактор: локальные файлы по-прежнему ограничены квотой браузера/диском и памятью при JSON-экспорте. При превышении облачного лимита исходный файл и локальная копия сохраняются, статус сообщает ошибку.

Приватные файлы выдаются владельцу через signed URL на 24 часа; если вкладка открыта дольше, перезагрузите её для обновления ссылок. Полная автономная работа с ранее облачными файлами не обещается: структура сохраняется локально, но браузерный кеш и доступность ранее полученных медиа зависят от сети. Для переноса без сети скачайте JSON со всеми файлами заранее.

В кабинете есть явная очистка с подтверждением. Сначала она сохраняет текущий черновик. Сервер под общей блокировкой помечает к удалению только приватные файлы старше 7 дней, отсутствующие в текущем черновике и активном снимке публикации; новые сохранения не могут сослаться на удаляемый файл. Затем удаляются байты и метаданные. Ошибку можно повторить без потери используемых файлов. У публичных файлов удаляются только копии старше суток, на которые не ссылается текущая публикация. Старые версии undo не хранятся на сервере: перед очисткой нужен экспорт. История отмены не является постоянной резервной копией.

Лимиты RPC на аккаунт: 180 сохранений/мин, 600 резервирований файлов/час, 10 публикаций/мин, 10 снятий/мин, 3 очистки/час; username меняется не чаще раза в минуту. В production остаётся настройка квот тарифа, мониторинга, общей квоты аккаунта и защиты от массовых регистраций.

## Перенос старого проекта

1. На прежнем адресе сайта откройте локальный проект, при желании скачайте JSON.
2. Нажмите «Сохранить в облако» и войдите/зарегистрируйтесь.
3. В кабинете нажмите «Перенести локальную страницу». Если в облаке есть черновик, подтвердите замену либо отмените и откройте его через «Редактировать».
4. Дождитесь проверки структуры, ревизии и доступности всех перенесённых файлов.
5. Локальный ключ `link-canvas.project.v1` и IndexedDB `link-canvas.files.v1` **не удаляются автоматически**. Только после проверки появится отдельная кнопка удаления исходной локальной структуры с подтверждением. Бинарные файлы останутся для редактора и отмены; очистка IndexedDB вручную требует резервного копирования.

JSON-экспорт работает и для облачного проекта: приватные файлы скачиваются и включаются в `assets` как base64. При импорте они получают новые локальные ID; в аккаунте затем загружаются в Storage. Внешние URL остаются внешними и не копируются автоматически — их доступность зависит от владельца, сети, кодеков и разрешений на встраивание.

## Публикация

«Опубликовать» сначала подтверждает сохранение черновика. Функция берёт серверный снимок конкретной ревизии и копирует **только используемые файлы** в отдельную папку публичного bucket. После всех успешных копирований PostgreSQL одной транзакцией заменяет опубликованную структуру. При сбое предыдущая публикация остаётся целой. Одновременные публикации и завершение уже отменённого задания блокируются.

На `/u/<username>` нет редактора и зависимости от localStorage автора. Посетитель читает только `published_pages` и публичные файлы. Изменения черновика не видны до «Обновить публикацию». Снятие удаляет публичную запись и отменяет активное задание, сохраняя черновик. Уже опубликованные файлы могут оставаться по прямым URL и в кешах до очистки; снятие публикации не отзывает скачанные посетителем копии.

## Проверки

```sh
npm run typecheck
npm test
npm run build
npm run test:e2e
npm run test:cloud
npm run test:e2e:cloud
```

Первые четыре команды не требуют серверных тестовых ключей. Последние две требуют работающий **локальный** Supabase с миграциями и функцией. Скрипты получают временный тестовый service key через локальный CLI только для подготовки/удаления собственных тестовых пользователей. Защита URL разрешает только loopback; рабочую базу они не используют. Не запускайте браузерные наборы одновременно — обоим нужен порт 5180.

`test:cloud` проверяет реальные Auth/PostgreSQL/RLS/Storage/Edge, а не подменённые ответы. `test:e2e:cloud` собирает production и проверяет регистрацию, перенос всех восьми типов и шрифта, чанковую загрузку WAV больше 10 МБ, просмотр отдельным анонимным браузером, воспроизведение, вход с другого устройства, JSON с облачными файлами, независимость черновика, повторную публикацию, смену адреса, снятие, CAS-конфликт, offline/reconnect, изоляцию аккаунтов и восстановление по письму Mailpit.

Для Chromium в текущей облачной среде используйте только `XDG_CONFIG_HOME=/tmp/link-canvas-browser/config XDG_CACHE_HOME=/tmp/link-canvas-browser/cache` перед браузерными командами. Результаты последней проверки см. в `docs/STAGE3-VALIDATION.md`.

Следующие этапы: рабочий HTTPS-деплой и SMTP, агрегированная квота/медиатека, автоматическая очистка по расписанию, мониторинг и постоянные резервные копии, полноценный offline-кеш, совместное редактирование и отдельные мобильные раскладки. Сейчас один проект на аккаунт, без совместного редактирования, собственного домена пользователя и серверного HTML/SEO-рендеринга.
