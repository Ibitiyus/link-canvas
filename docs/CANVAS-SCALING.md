# Одна композиция на всех экранах

Ширина `project.page.maxWidth` теперь является **логической шириной полотна**, а не ограничителем адаптивной сетки. Например, при 960 px поверхность всегда имеет ширину 960 CSS px, внутренние отступы по 20 px и сетку шириной 920 px. Значения старых проектов (в том числе 880 px по умолчанию) сохраняются. Формат v1, данные базы, координаты, размеры, `colSpan` и `rowSpan` не мигрируют и не меняются при просмотре.

## Размещение и масштаб

`Canvas` создаёт одну логическую сетку для редактора, предпросмотра и `/u/:username`. `CanvasViewport` помещает её целиком в единственный контейнер с `transform: scale(...)`, начало преобразования — левый верхний угол. Масштабируются сразу обе оси: текст, отступы, рамки, медиа, QR, размеры/координаты/повороты декора. Мобильные панели редактора остаются адаптивными; пользовательские блоки не перестраиваются.

Обычный масштаб — `min(1, availableWidth / compositionWidth)`. Если декора за границами нет, `compositionWidth` равна сохранённой ширине полотна. Если есть отрицательные координаты или выход справа, общая область расширяется по повёрнутым границам декора, с запасом 12 логических пикселей. Режим «По ширине» вписывает **всю композицию**, включая такие элементы. Поэтому справа/слева ничего не обрезается и нет неожиданной горизонтальной прокрутки. Оригинальные координаты декора остаются пиксельными относительно начала сетки; область вокруг неё добавляется только при отображении.

`ResizeObserver` следит за доступной шириной и фактической логической высотой содержимого. Внешний контейнер получает реальные размеры `compositionWidth * scale` и `compositionHeight * scale`; абсолютный трансформируемый контейнер не оставляет немасштабированный след в потоке. Одинаковые измерения не вызывают повторного обновления состояния. Повороты и нижний декор включаются в высоту, в том числе после редактирования/отмены.

Кнопки «+», «−» и «По ширине» находятся вне трансформации и работают во всех трёх режимах. Ручной масштаб допускает увеличение до 400%; увеличенное полотно прокручивается внутри собственной области, а вертикальная прокрутка документа сохраняется. Кнопка «По ширине» возвращает автоматический коэффициент. Масштаб — локальное состояние просмотра; он не попадает в localStorage проекта, историю, JSON или Supabase. Собственный pinch-жест не добавлен; обычное браузерное увеличение не запрещено.

При перетаскивании/изменении размера смещения указателя по **обеим** осям переводятся обратно в логические пиксели. Шаг сетки также учитывает масштаб. Декор блокирует сенсорную прокрутку только в режиме редактирования; на публичной странице он не перехватывает обычную прокрутку.

Фоновое изображение теперь рисуется внутри логического полотна одинаково во всех режимах, а не независимо на размере экрана предпросмотра. Снаружи остаётся сохранённый цвет фона. Содержимое блоков не получает мобильных переопределений отступов. Размер контейнера аудиоплеера определяется логической шириной блока, поэтому его внутренние container queries одинаковы на всех экранах.

Геометрия не зависит от viewport. Сами системные шрифты Arial/Georgia/system-ui и emoji могут иметь разные метрики/рисунок в разных ОС; для одинаковой типографики на разных платформах используйте один загруженный WOFF2/TTF либо поставляемый с ZIN шрифт. Существующие шрифтовые настройки намеренно не заменяются другим шрифтом. Сглаживание и стандартные элементы видеоплеера также определяются браузером.

## Проверки

```sh
npm run typecheck
npm test
npm run build
TEST_PRODUCTION=1 npm run test:e2e
npm run test:canvas
```

`test:canvas` собирает production с **фиктивным локальным** публичным ключом, затем перехватывает только чтение опубликованной страницы в Playwright. Рабочий Supabase и данные сайта не используются. После этой команды обычный `npm run build` восстановит сборку с вашими переменными окружения — тестовую папку `dist` не следует развёртывать как рабочую.

Тестовая композиция содержит 4 колонки, разные размеры блоков, все 8 типов, текст, изображение, настоящий GIF/WebM/WAV, QR, стикер поверх изображения, повёрнутый декор с отрицательными координатами и элемент ниже/правее сетки. Для **редактора, предпросмотра и публичного маршрута** проверяются ширины 1440, 1024, 768, 390 и 320 px.

Проверки сравнивают нормализованные `getBoundingClientRect` (допуск 0,12 логического пикселя), порядок/размеры/пропорции, 4 колонки, прямоугольники строк текста, нижнюю границу, доступность нижнего декора и отсутствие горизонтального переполнения. Изменение viewport и масштаба не меняет проект. Проверены нажатия касанием по ссылке/QR, реальное воспроизведение аудио/видео, сенсорная перемотка, координаты drag по обеим осям и пересчёт высоты.

Для публичной композиции сохранены **5 визуальных эталонов Linux/Chromium** в `tests/canvas-scaling.spec.ts-snapshots/`. Эталоны после создания повторно проверены обычным запуском без `--update-snapshots`; GIF и видео маскируются только при сравнении изображений, чтобы смена кадра не давала ложную разницу. Медиа-взаимодействия проверяются отдельно без масок. На другой ОС Playwright использует отдельные эталоны по своему стандартному соглашению.

В текущей облачной среде браузерным командам нужны `XDG_CONFIG_HOME=/tmp/link-canvas-browser/config XDG_CACHE_HOME=/tmp/link-canvas-browser/cache`. Не запускайте два набора Playwright одновременно: используется порт 5180.

Итог: TypeScript и production build прошли; **72 модульных теста** (11 файлов), **33 прежних браузерных сценария**, **6 новых сценариев масштабирования** прошли. В общем наборе публичный mock-сценарий пропускается без специальной тестовой конфигурации; отдельный `npm run test:canvas` выполнил все 6 сценариев без пропусков.

Дополнительно выполнены 36 проверок настоящего локального Supabase и облачные сценарии `npm run test:e2e:cloud` (регистрация, миграция, шрифты/медиа, другое устройство, независимая публикация, конфликты/offline и восстановление пароля). Настройки рабочего Supabase и существующие данные не менялись.

Снимки одной композиции: [ПК, 1440 px](screenshots/scaling-desktop.png), [телефон, 390 px](screenshots/scaling-mobile.png).

## Проверка после деплоя

1. Объедините PR `feat/consistent-canvas-scaling` в `main`, дождитесь успешного production-деплоя Vercel. SQL-миграций и новых переменных окружения для этой задачи нет.
2. На компьютере откройте старую страницу: её сохранённая ширина, количество колонок и значения размеров должны остаться прежними. Добавьте текст, фото, GIF/видео/музыку, QR и стикер поверх фото. Для проверки границ задайте одному декору отрицательные X/Y, другому — положение ниже сетки.
3. Сравните редактор и предпросмотр. Опубликуйте тестовую страницу и откройте её `/u/:username` на телефоне/планшете и в отдельном анонимном браузере. В режиме «По ширине» должна сохраняться композиция, переносы при одинаковом файле шрифта, наложение стикера и число колонок.
4. Нажмите «+», прокрутите увеличенное полотно до правого/нижнего декора, нажмите «−» и «По ширине». Проверьте ссылки, QR, play/pause и перемотку. Поверните телефон: меняется только общий масштаб.
5. Обновите страницу; проверьте, что смена масштаба не изменила сохранённые размеры/координаты. Изменение черновика по-прежнему не должно менять публикацию до явного обновления.

Внешний рабочий адрес `https://link-canvas-swart.vercel.app` из текущей среды отвечает HTTP 403 через сетевой прокси. Поэтому проверены локальная production-сборка и настоящий локальный backend; результат на рабочем домене после будущего деплоя пока не подтверждён.
