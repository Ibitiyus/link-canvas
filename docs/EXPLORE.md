# Explore: публичная галерея ZIN

## Что изменилось

`/explore` доступен без входа и без загрузки локального/облачного черновика. Карточки содержат опубликованные название, описание, категорию, дату обновления, актуальный username и ссылку `/u/:username`. Есть поиск с задержкой 350 мс, 9 категорий, сортировки «Новые», «Недавно обновлённые», «Случайные», порции по 12 и повтор запроса после ошибки. Запрос/категория/сортировка сохраняются в URL. Новые — по дате первого согласия, обновлённые — по последней публикации композиции или представления. Случайная выдача использует фиксированный seed до нажатия «Перемешать».

Ни одна существующая публикация не включена автоматически. В `/dashboard` появилась секция «Публикация в галерее»:

1. Заполните название (1–80 символов), описание (до 280), категорию и необязательную обложку.
2. «Сохранить до публикации» сохраняет только приватные настройки. «Опубликовать представление» явно обновляет публичные метаданные уже опубликованной страницы. Обычная публикация/повторная публикация страницы также фиксирует настройки, даже если композиция не изменилась.
3. «Показывать мой ZIN в галерее» сохраняет согласие немедленно, отдельно от формы. Оно не публикует несохранённый текст формы. До публикации самой страницы карточки не будет.
4. Выключение немедленно исключает страницу из **новых серверных запросов** каталога/поиска, сохраняя прямой публичный адрес. Уже открытый список не получает realtime-уведомлений — обновите его. Снятие с публикации также исключает карточку. Сохранённое выключенное согласие не включается при повторной публикации; включённое сохраняется.

Изменение username обновляет ссылку через существующий FK cascade; оно не публикует черновые настройки. Редактор, JSON проекта, IndexedDB, localStorage, группы, эффекты и геометрия не менялись. Метаданные галереи принадлежат аккаунту и намеренно не входят в JSON композиции.

## Обложки и производительность

Это **выбранная автором обложка, не автоматический снимок страницы**. Без изображения показана подписанная типографическая карточка «БЕЗ ОБЛОЖКИ». Тестовая JPEG-обложка создана в репозитории как собственный геометрический рисунок без сторонних ресурсов. Никаких фиктивных пользователей или записей в production нет; персонажи на тестовых скриншотах существуют только в Playwright fixtures.

PNG/JPEG/WebP с устройства преобразуется браузером в статичный JPEG 480 × 300, до 64 КиБ; метаданные/анимация исходника не переносятся. Исходник ограничен 20 МиБ только для этого конвертера, обычные лимиты редактора не менялись. SQL проверяет MIME data URL, base64, размер файла, JPEG-маркеры, SOF ширину ≤480 и высоту ≤300. SVG/GIF, внешние URL, blob URL и файлы с чрезмерными размерами не принимаются сервером. Изображение выводится только через `<img>`, с lazy loading, async decoding и запасным состоянием при ошибке.

Крохотная обложка хранится в TOAST-поле приватных настроек и его опубликованном снимке. Не создаются копии полного проекта и не открываются приватные Storage-файлы. RPC не читает project JSON и возвращает только компактную публичную проекцию; карточки не монтируют Canvas, GIF, видео, аудио, шрифты или анимации страниц. На порцию из 12 худший объём самих обложек около 1 МиБ base64; обычно значительно меньше. Это простой надёжный вариант первой версии. На большом каталоге имеет смысл вынести миниатюры в отдельный public bucket/CDN с ETag и отдельными запросами. Текущие миниатюры повторно передаются в RPC, хотя декодируются лениво.

Пагинация серверная offset, максимум 24 строки в запросе и глубина 10 000. Есть индексы категории/даты и pg_trgm поиска. Изменения каталога между запросами могут сдвигать страницы; клиент убирает повторные username. Random сортировка требует вычисления порядка среди подходящих строк; для очень большого каталога потребуются keyset pagination, отдельный поисковый индекс и предварительная случайная выборка. Не вводились рейтинги или фиктивная популярность.

## Безопасность и модерация

- `explore_settings`: RLS, владелец читает только свою строку. Прямые INSERT/UPDATE/DELETE запрещены клиентским ролям; RPC выводят owner только из `auth.uid()`. Публичный RPC объединяет настройки с **существующей публикацией**, требует `listed=true`, исключает модерационное скрытие и не отдаёт owner UUID, email, черновые поля или project.
- `explore_moderation`: нет клиентского чтения/записи. Авторы не могут снять административное скрытие переключением согласия, новой публикацией, снятием с публикации или переименованием.
- `explore_reports`: нет клиентского чтения/записи. Через RPC зарегистрированный пользователь может отправить причину и до 500 символов деталей. Контактные данные не запрашиваются и не публикуются; reporter UUID доступен только серверу/оператору. Максимум 5 успешных отправок в сутки на аккаунт, повторная жалоба на ту же страницу обновляет существующую. Автор страницы не получает личность отправителя.
- SECURITY DEFINER использует пустой search_path, явные grants и параметры без динамического пользовательского SQL. Символы `%`/`_`/`\` в поиске буквальные, длины/порции/категории/сортировки проверяются сервером. В пользовательских полях нет HTML-рендеринга.
- Изменения настроек, согласия и публикации сериализуются существующей блокировкой profile. Клиентские запросы привязаны к инициировавшему аккаунту, а старые запросы поиска отменяются.

Жалобы требуют входа для ограничения спама; анонимный посетитель получает объяснение и ссылку входа. Публичной административной панели и автоматического удаления по числу жалоб нет. Для реальной эксплуатации владелец обязан назначить ответственного и сроки обработки, подготовить правила контента/правообладания, процедуру обжалования, сроки хранения жалоб и серверные журналы модерации. Настройте rate limits регистрации/CAPTCHA из [PRODUCTION_READINESS.md](PRODUCTION_READINESS.md), мониторинг и WAF/API rate limiting для анонимного поиска. Клиентский debounce не является защитой от API-злоупотреблений.

### Административное скрытие

Только в доверенной серверной среде с service-role key (никогда в Vite, браузере, URL или логах):

```js
const { error } = await serverSupabase.rpc('moderate_explore', {
  page_username: 'actual_username',
  hide: true,
  moderation_reason: 'Краткая внутренняя причина'
});
if (error) throw error;
```

`hide:false` снимает скрытие, но не включает согласие автора. RPC доступен только `service_role`; обычный пользователь/anon получают отказ. Оператор также может работать из доверенного SQL Editor:

```sql
-- Просмотр закрытой очереди без email и публикации идентификаторов наружу.
select r.created_at, p.username, r.reason, r.details
from public.explore_reports r join public.profiles p on p.id=r.subject_id
order by r.created_at desc limit 100;
select public.moderate_explore('actual_username', true, 'Проверено оператором');
```

Не выводите пользовательские details как HTML в будущих инструментах оператора. Операции не удаляют страницу, публикацию или файлы; прямой публичный адрес остаётся рабочим. Для опасного контента потребуется отдельная политика снятия **самой публикации**, это не реализованный здесь публичный каталог модерации.

## Развёртывание — действия владельца

Production Supabase/Vercel из среды разработки **не изменялись**. Новые миграции применялись только к локальному Docker Supabase. Данные пользователей не переносились и не удалялись.

1. Сделайте резервную копию БД. Убедитесь, что миграции Stage 8 уже применены. Просмотрите diff/PR и проверку RLS ниже.
2. Примените **по порядку** новые миграции обычным процессом Supabase CLI после проверки целевого проекта либо по одной в SQL Editor:
   - `202610230001_explore_gallery.sql`: таблицы, RLS/grants, индексы, RPC, снимок метаданных. Устанавливает pg_trgm в extensions, если его ещё нет; поддерживает уже установленное расширение в другой схеме.
   - `202610230002_explore_projection.sql`: компактная проекция без чтения JSON композиции, кеш исходного публичного названия.
   - `202610230003_explore_idempotent_publish.sql`: фиксация метаданных при повторной публикации неизменившейся композиции.
   - `202610230004_explore_cover_bounds.sql`: серверная проверка JPEG и безопасных размеров миниатюр.
3. После миграций разверните обновлённую Edge Function: `supabase functions deploy page-actions`. Старые миграции/бакеты/SQL/настройки Auth не редактировать. Новых секретов, бакетов и дополнительных переменных окружения нет.
4. Только затем деплой frontend из этой ветки/после merge. Существующий `vercel.json` с SPA rewrite остаётся прежним и обслуживает `/explore` и `/u/:username`. Сохраните текущие `VITE_SUPABASE_URL` и публичный anon/publishable key; service-role не помещать в Vite.
5. Актуальный production-домен следует взять из **Vercel → Project → Domains → Production**. В checkout нет `.vercel/project.json` или подтверждённого production-domain setting; README/документация содержат только прежний исторический адрес. Исходники не позволяют надёжно подтвердить, что он по-прежнему основной. Поэтому новые ссылки и OG URL используют **`location.origin`**, никакого старого адреса в реализации нет. В Auth Site URL/Redirect URLs остаются действующие настройки владельца; этот этап их не меняет.
6. Проверьте на действующем production-домене `/explore` без входа: сначала галерея пустая. В тестовом аккаунте создайте страницу, опубликуйте и проверьте, что без согласия её нет в каталоге. Сохраните оформление карточки, опубликуйте представление, включите согласие. Откройте приватное окно, проверьте поиск/категорию, карточку и `/u/:username`.
7. Измените название карточки и нажмите только «Сохранить до публикации»: посетитель должен видеть прежнее. Затем опубликуйте представление/страницу — посетитель увидит новое. Проверьте повторную публикацию без изменения композиции.
8. Выключите согласие: в обновлённом Explore карточки нет, прямой URL работает. Повторная публикация не должна включить согласие. Включите снова, смените username и проверьте новый маршрут. Снимите страницу с публикации: в каталоге её нет.
9. Проверьте 2 аккаунта: B не читает настройки/жалобы A и не изменяет их через REST; anon не вызывает owner/moderation RPC. Отправьте тестовую жалобу, просмотрите закрытую очередь, скройте страницу service-role RPC. Переключение автором галочки и повторная публикация не должны отменять скрытие. Снимите тестовое скрытие, не включая согласие за автора.
10. Проверьте 320/390/768/1440 px, клавиатуру, Escape и возврат фокуса в диалоге, медленную сеть/повтор запроса, отсутствие запросов к оригинальным медиа страниц в карточках. Следите за SQL latency, количеством запросов и размером БД/трафиком обложек. Не используйте `cloud:reset`/`db reset` на production.

## SEO и ограничения

Заголовок, description и Open Graph Explore устанавливаются клиентом; `og:url` берёт текущий origin. Приватные экраны получают `robots=noindex,nofollow` для выполняющих JavaScript роботов. Это SPA без SSR/серверных OG-превью: гарантировать индексацию, соцсетевые карточки и noindex для роботов без JS нельзя. Приватность обеспечивают Auth/RLS, а не robots. Для строгого noindex владелец может дополнительно настроить X-Robots-Tag на приватных маршрутах в Vercel; активная конфигурация этого этапа не менялась.

Публичная галерея не включает лайки, подписки, комментарии, рейтинг, личные сообщения, публичную модераторскую панель или автоматическое обнаружение контента. Публикация не означает согласие на Explore.

## Воспроизводимые проверки

```sh
npm run typecheck
npm test
npm run build
npm run test:explore     # только локальный Supabase: новые реальные RLS/RPC/Edge проверки
npm run test:cloud       # существующие реальные Auth/Storage/публикация/конфликты
# Если запускаете Chromium в облачной среде:
export XDG_CONFIG_HOME=/tmp/link-canvas-browser/config
export XDG_CACHE_HOME=/tmp/link-canvas-browser/cache
npm run test:e2e:cloud   # собирает приложение с локальным настоящим ключом и выполняет cloud-platform
```

Обычные `tests/explore.spec.ts` перехватывают серверные ответы, проверяют UX, запросы и безопасность DOM. Для запуска вместе со всеми тестами геометрии/публичного отображения:

```sh
VITE_SUPABASE_URL=http://127.0.0.1:54321 VITE_SUPABASE_ANON_KEY=zin-local-renderer-test npm run build
TEST_PRODUCTION=1 ZIN_CANVAS_E2E=1 npm run test:e2e -- --workers=1 --trace=off
```

Тесты интеграции отказываются подключаться вне loopback, создают временные тестовые аккаунты и удаляют только их в finally. Не запускайте эти сценарии против production. Для исходников Edge после изменений нужен перезапуск локального worker, а не сброс данных.

**Полный прогон не объявляется полностью зелёным.** Нестабильность ожидания автосохранения в старом составном тесте группировки под нагрузкой остаётся ограничением CI; отдельный успешный повтор не доказывает её устранение. В helper добавлено ожидание готовности редактора для reload, но код автосохранения ради результата тестов не менялся. Более ранний полный запуск имел 118/119 с ожиданием большого изображения; повтор со сбором trace получил тайм-ауты выполнения/teardown и был остановлен. Итоговые числа выше относятся к завершённому запуску без trace. Логи и диагностические trace сохранены в `/tmp/zin-explore-*` текущей рабочей среды; они не содержат service key и не являются артефактами production.

Production Supabase, реальный Vercel-деплой и внешний SMTP этими локальными проверками не подтверждены. Скриншоты локальных тестовых карточек: [desktop](screenshots/explore/gallery-1440.png), [mobile](screenshots/explore/gallery-390.png).
